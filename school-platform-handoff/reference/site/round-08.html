학교별 개선 요청

예를 들어 룽아룬숙사가 “학부모 휴대폰에서 태국어 성적표를 열고 싶다”고 요청하면 다음 순서로 처리하는 설계입니다.

  1. 학교 등록학교 ID와 전용 요청 판을 만듭니다. 최초 설정 작업이 있으면 온보딩 이슈를 연결합니다.
  2. 요청 접수학교는 자기 요청의 상태를 확인합니다. 동일 요청 ID는 한 번만 등록하고, 학생 원본 자료는 학교 내부에 둡니다.
  3. 개발 채택운영자가 범위와 우선순위를 정합니다. 성적표 열람은 공통 모듈에, 언어와 양식은 학교 설정에 반영합니다.
  4. 개발·학교 검토비식별 이슈별 브랜치에서 구현하고 테스트합니다. 학교는 차시별 시안 주소에서 결과를 확인합니다.
  5. 배포·기록검수한 변경을 배포하고 적용 학교, 요청 ID, 배포 버전과 검토 의견을 연결합니다.

공통 학사 기능과 학교별 확장

학사 운영의 공통 로직은 하나의 버전 패키지로 유지하고 학교별 설정과 전용 코드만 분리하는 안입니다. 메뉴·화면·입력 필드·계산 규칙·보고서·이벤트 처리·테마를 공식 확장 지점으로 둡니다.

룽아룬숙사의 학기와 태국어 성적표를 설정만으로 적용해 보고, 별도 코드가 필요한 부분을 기록합니다. 학교마다 저장소와 배포를 분리할지, 같은 저장소의 설정으로 유지할지는 첫 두 학교의 도입·갱신 시간을 비교해 결정합니다.

학교 자료와 업데이트 경계

공유 DB에 학교별 스키마와 접속 역할을 두는 안과 학교별 프로젝트를 비교합니다. 가상 자료로 타 학교 접근 차단을 확인하고, 학교별 코어 버전·변경 적용 결과·재시도 상태를 관리 화면에 표시하는 것이 검증 과제입니다.

일반 업데이트는 학교가 검토한 뒤 적용하고, 보안 수정은 공통 배포 경로를 따르는 안입니다. 학교 전용 배포 비용과 관리 시간을 실측한 후 요금에 반영합니다.

Mac에서 GitHub로 옮기는 순서

  1. 코드와 학교 자료를 구분하고 클라우드에 보낼 소스를 확인합니다.
  2. 로컬에서 하던 배포 전 검사를 GitHub Actions에 옮겨 시안에서도 같은 기준을 통과하는지 검증합니다.
  3. 세션별로 필요한 최소 권한을 정하고, 앱 단위로 클라우드 세션을 시범 운영합니다.

기존 개선 요청 판을 진행 상태의 기준으로 유지합니다. GitHub 이슈·PR은 작업 증빙으로 연결하고, 상태를 두 곳에서 따로 관리하는 부담을 피합니다.

학교 전용 구독안과 현재 손익 가정

현재 손익표는 운영자가 채택한 내부 개발에 기존 구독을 쓰는 모델입니다. Claude 문서의 학교 전용 좌석은 독립 대안입니다. 학교가 직접 계약하고 승인된 사용자가 공식 도구를 쓰는 경우와 운영사가 좌석을 할당·재판매하는 경우의 계약 조건이 다릅니다. 기본료에 좌석을 포함하는 안은 공급사 계약·견적 확인 전입니다.

시범 운영에서는 학교별 작업 수·검수 시간·한도 대기·추가 API 비용을 기록해 두 방식의 비용을 비교합니다. 월 손익 화면의 구독·CI 추가비로 증액 영향을 시험할 수 있습니다.
