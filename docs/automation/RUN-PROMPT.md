# 자동 개선 실행 절차 (예약 작업이 매번 따르는 지시)

이 파일은 예약 작업이 새 세션에서 읽고 그대로 따른다. 규칙은 `AUTOPILOT.md`의 안전 규칙이 우선한다.

## 0. 준비
1. 저장소 `namoogi/school-platform`을 세션에 연결하고 받는다(얕은 클론).
2. `AGENTS.md`, `docs/automation/AUTOPILOT.md`, `docs/automation/DIRECTION.md`(방향 설계), `docs/automation/QUEUE.md`, `docs/COLLABORATION.md`를 읽는다. 관제 센터 `/api/control/mine`과 연구소 항목(`/api/admin/items`)도 본다.
   - `/api/control/mine?session=<내 id>`에서 `due: true`인 내 기한 진행 카드가 있으면 그 카드의 `default_action`을 먼저 실행하고, 같은 요청에 `{"kind":"report","status":"done"}`로 보고한다(ADR 0048).
3. 기준 브랜치를 정한다: main에 `package.json`이 있으면 main. 없으면 열린 PR 중 다른 PR의 기준이 되지 않는 가장 최근 `round-*` 브랜치(쌓인 PR의 끝).
4. 검토 대기 `[자동]` PR 수(진행 중 제외)를 센다. 3개 이상이면 새 기능을 시작하지 않는다(이어가기는 한다).
5. 로컬 Postgres 16을 54322 포트로 띄우고 `npm ci`. (방법은 README '로컬 실행')
6. **이어가기 확인** (새 작업보다 먼저):
   - 제목에 `[자동·진행 중]`이 붙은 열린 PR의 마지막 커밋이 **40분 안**이면 다른 실행이 작업 중이다 → 아무것도 하지 않고 "다른 실행 진행 중"만 보고한다.
   - 40분 넘게 멈춘 `[자동·진행 중]` PR이 있으면 → 1단계를 건너뛰고 그 PR 브랜치를 받아 **남은 작업을 이어서 끝낸다**. PR 본문의 '남은 일' 목록부터 본다.

## 1. 종류 고르기 (하나만)
자동 세션은 대기열만 처리하지 않고 **방향 설계**를 맡는다(2026-11-27 사용자 지시, `DIRECTION.md`). 아래 순서에서 처음 걸리는 하나를 고른다.
- 0순위. 관제 센터에서 나에게 온 답·지시, 내 PR의 Codex 지적 반영
- D. `DIRECTION.md` 3절 '다음 후보' 맨 위의 **자동 허용** 항목(UI 점검 표 포함). 승인 필요 항목은 설계 문서를 쓰고 관제에 **결정 카드**를 올린다(아래 '결정 카드')
- A0. `QUEUE.md` 맨 위 **UI 점검** 표: 자체 점검이 `대기`이고 같은 페이지의 열린 `[자동] UI 점검` PR이 없는 맨 위 페이지 → 그 표의 절차(85차)
- A. `QUEUE.md`에서 맨 위의 **자동 허용** 항목 중, 같은 주제의 열린 PR이 없는 것 → 기능 구현
- B. A가 없으면: `docs/decisions/`·`docs/design/DESIGN-SYSTEM.md`와 실제 코드가 어긋난 곳(색 값 직접 사용, 페이지 헤더 누락 등)을 찾는다 → 설계 갱신 문서 또는 작은 정리 PR
- C. A·B가 없으면: 최근 "주간 점검" 이슈와 `npm outdated`·`npm audit` → 의존성 갱신(공개 2주 지난 버전만) 또는 도구 비교 결정 기록 초안

## 2. 작업
- 브랜치 `auto/<YYYY-MM-DD>-<주제>` (기준 브랜치에서)
- **시작하자마자 초안(draft) PR을 연다.** 제목 `[자동·진행 중] <종류> · <주제>`, 본문에 '계획'과 '남은 일' 체크 목록.
- 단계 하나를 끝낼 때마다 커밋·push하고 '남은 일'을 갱신한다(다음 실행이 이어받는 기준이며, 마지막 커밋 시각이 '작업 중' 신호다).
- **기능이 끝나고 3단계 검사가 통과할 때까지 멈추지 않는다.** 시간이 모자라 끝내지 못하면 '남은 일'을 정확히 적고 끝낸다(다음 실행이 이어 감).
- 데이터 경계·디자인 시스템·마이그레이션 규칙을 지킨다. 새 마이그레이션이 필요하면 초안 PR로만.
- 바뀐 동작에는 테스트를 더한다.

## 3. 검사
`npm run typecheck`, `npm run test:unit`, `npm test`, `npm run build && npm run test:e2e` (E2E는 화면을 바꿨을 때). 실패를 고치지 못하면 PR을 초안으로 두고 실패 내용을 적는다.

## 4. PR (완료 처리)
- 끝나면 제목을 `[자동] <종류> · <주제>`로 바꾸고 초안을 해제한다. 기준 브랜치는 0-3에서 정한 브랜치, PR 양식(.github/pull_request_template.md)을 채운다.
- `docs/automation/runs/<YYYY-MM-DD>.md` 실행 기록을 같은 PR에 넣는다.
- PR 댓글로 `(Claude 자동 실행 작성)\n@codex review` 를 요청한다.
- 0단계에서 열린 PR 중 **Codex 리뷰 댓글**이 달렸는데 반영 안 된 것이 있으면, 새 작업보다 먼저 반영(작은 지적은 고치고, 큰 제안은 답글로 정리해 사용자 판단 요청)한다.
- `codex/` 브랜치 PR이 있으면 AGENTS.md Review guidelines로 검토 댓글을 남긴다(병합하지 않는다).
- 설계 작업(B 종류)에서 안 B가 필요하면 이슈를 열어 `@codex` 작업 요청을 남긴다(COLLABORATION.md 8절).
- QUEUE.md의 해당 항목 상태를 "진행 중 (PR #n)"으로 바꾼다.

## 5. 보고
- 실행 끝에 `DIRECTION.md` 3절 상태·순위를 갱신한다(연구소에 새 항목이 생겼으면 후보에 넣거나 넣지 않은 이유를 적는다).
세션 마지막 메시지에 한 일, PR 링크, 테스트 결과, 승인 필요 항목을 5줄 안으로 적는다(AGENTS '선생님께 설명할 때' 순서: 요약 → 왜 → 처음 나오는 용어 풀이). 할 일이 없었으면 "변경 없음"과 이유만 적고 PR을 만들지 않는다.

## 결정 카드 (ADR 0048)
사람 판단이 필요하면 `POST /api/control/requests`에 결정 카드로 올린다. 형식·예시는 `docs/automation/DECISION-CARDS.md`가 기준이다(칸이 빠지면 400).
| 문(`door`) | 자동 세션에서 쓰는 경우 | 꼭 있어야 하는 칸 |
| --- | --- | --- |
| `notice` | 화면·문서·시험 정리처럼 고를 것이 없는 진행 보고 | `title`, `changes` |
| `default` | 되돌릴 수 있지만 방향이 갈리는 것(화면 구성·명칭·순서). 기한은 보통 2~3일 | `title`, `ask`(예/아니오, 물음표), `changes`·`unchanged`·`undo`, 선택지 2~4개 + `recommended`, `due_at`(ISO 8601 + 시간대, 30일 안), `default_action`, `source_session` |
| `one_way` | 삭제·덮어쓰기, 비용, 공개 범위 확대, 외부 발송, 권한 확대만 | `default`의 칸에서 `due_at`·`default_action` 빼고 모두. 답이 올 때까지 보류하고 다른 일을 한다 |
- 사용자가 직접 시킨 일은 카드를 올리지 않는다(지시가 곧 승인).
- 분류가 애매하면 한 단계 위로 올린다(알림 → 기한 진행 → 한쪽 문).
- 기한이 지나 추천안으로 진행했으면 PR 본문에 "추천안으로 진행함(D-n)"을 적는다.

## 하지 않는 일
병합, main 직접 push, 배포·환경 설정 변경, 유료 API, 결제, 외부 발송, 이미 적용된 마이그레이션 수정, 한 실행에 새 기능 두 개 이상, 다른 실행이 작업 중인 PR 건드리기.
