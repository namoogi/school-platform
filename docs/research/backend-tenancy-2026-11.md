# 학교별 커스텀 백엔드 — 드리미포털 방식 적용 검토 (2026-11-26)

- 요청: 선생님 — "드리미포털의 현재 백엔드 방식을 받아 분석해서, 적용할 수 있는지 아니면 위험한지, 상용 서비스로는 무엇이 나은지 비용·관리 측면을 함께 보자."
- 배경: 학교 플랫폼은 Supabase 프로젝트 1개 + 공용 표(`school_id` + RLS)다. 학교 AI는 표·서버 코드를 만들지 못한다(ADR 0025 '에이전트 DDL·코드 업로드 없음'). 선생님은 이것이 "학교별로 AI로 커스텀 기능을 만드는 것"을 막는다고 보았다.

## 1. 드리미포털 방식 (포털 답 요약)

| 항목 | 포털 |
|---|---|
| DB | Supabase **프로젝트 1개**, 앱마다 `app_<번호>` **스키마 한 칸**(앱 49개, 스키마 48) [잼] |
| 배포 | **Vercel 프로젝트를 앱마다 하나**(48개, 계정 전체 57개) [잼]. Vercel은 프로젝트 수로 과금하지 않음 |
| 새 앱 | 신청 → 관리자 승인 한 번 → 자동으로 스키마 배정·GitHub 템플릿 저장소·Vercel 프로젝트·환경 변수·웹훅·서브도메인까지 만든다(30~60초) [잼] |
| 표 만들기 | 콘솔이 아니라 `dreami.tables.json`에 선언하면 배포 때 포털이 없는 표만 만든다 [잼] |
| 로그인 | 포털이 OIDC 제공자('드리미로 로그인'). 사용자 표는 포털이 주인 [잼] |
| 앱 → 포털 | 공용 API 창구 `/api/platform/*` + 앱별 허용목록 + 사용량 장부 [잼] |
| 충돌 방지 | 마이그레이션은 한 폴더(560개). 병렬 세션 채번 충돌(14번호·28파일)을 겪었고, 도구로는 못 막았다. 결국 '배포를 세우는 문'으로 막았다 [잼] |
| 장애 번짐 | 배포가 따로라 앱 하나가 깨져도 나머지는 돈다. 다만 DB가 한 그릇이라 느린 질의 하나가 전체를 느리게 만든 적이 있다 [잼] |
| 권한 | RLS가 붙은 표는 소수다. 대부분 service key로 앱을 통해서만 접근한다 [잼] |
| 비용 | Supabase Pro 하나 + Vercel. 추가 과금의 주범은 DB가 아니라 Vercel 빌드 시간이었다 [잼] |
| 포털의 권고 | "한 DB 공유가 상용에서 가장 큰 위험이다. **학교 경계는 프로젝트(DB)로 가르고, 앱 칸(스키마)은 한 학교 안에서만** 쓰라" |

## 3. 포털 방식을 그대로 가져오면 [판단]

**가져올 만한 것** (포털도 같은 의견)
1. **한 번 누르면 서는 프로비저닝**: 저장소·배포·환경 변수·서브도메인이 자동으로 선다.
2. **git·토큰 없이 배포**: 학교 AI나 교사가 도구 사정에 걸려 멈추지 않는다.
3. **표를 선언으로 만들기**(`tables.json`): 날 DDL이 아니라 플랫폼이 검사한 뒤 만든다. 이름공간·RLS 필수 같은 규칙을 서버가 강제할 수 있다.
4. **공용 API 창구 + 앱별 허용목록 + 사용량 장부**: 우리에게도 비슷한 것이 이미 있다(범위 토큰 `agent_tokens`, 사용량 `usage_events`).
5. **OIDC 로그인 공유**: 학교 앱이 onschools 로그인으로 붙는다.

**그대로 가져오면 위험한 것**
1. **여러 학교가 DB 한 그릇에 같이 산다.** 포털은 한 학교라 견딘다. 상용에서는 세 가지가 문제다.
   - 한 학교의 무거운 질의나 학교 AI가 만든 나쁜 질의가 모든 학교를 느리게 한다.
   - 백업·복원이 프로젝트 단위라 한 학교만 되돌릴 수 없다.
   - 학교 AI가 만든 코드가 다른 학교 기록과 같은 DB에서 돈다.
2. **service key 중심 권한.** 포털은 앱이 유일한 문이라 그 문이 틀리면 막을 두 번째 담이 없다. 우리 핵심은 반대다.
   - 모든 표에 RLS를 걸었다.
   - 사용자 요청은 늘 `asUser`로 처리한다.
   - 열람 계정 전수 점검을 시험에 넣었다.

   이 장점을 버리면 안 된다.
3. **한 폴더 수동 채번.** 학교마다 앱이 생기면 마이그레이션이 폭증한다. 포털도 '배포를 세우는 문'으로 겨우 막았다. 우리는 날짜 접두어 + `check:repo` + 77~79차 Actions 문이 있지만, 학교 앱 표까지 이 폴더에 넣으면 같은 문제가 온다.

## 4. 선택지 비교

가정 [추정]: 학교 1곳 = 계정 30명, 파일 2GB. 확장 앱을 실제로 쓰는 학교 비율 = 20%. Vercel 빌드·함수 사용량은 별도(포털 경험상 빌드 시간이 가장 큰 변수).

| 안 | 구조 | 학교 AI 자유도 | 격리 | 월 비용 100곳 [추정] | 월 비용 1,000곳 [추정] | 관리 부담 |
|---|---|---|---|---|---|---|
| **1. 지금 유지** | 공용 핵심만, 정의 엔진 안에서 확장 | 낮음~중간 | 핵심 RLS로 학교 경계 | ~$60~110 | ~$200~500 | 가장 낮음 |
| **2. 포털식 그대로** | 공용 DB 하나에 학교·앱마다 스키마, 앱마다 Vercel | 높음 | **약함**(DB 공유, 학교 AI 코드가 같은 DB) | ~$60~150 | ~$300~700 + 큰 컴퓨트 | 중간. 장애·느림이 모두에게 번짐 |
| **3. 학교마다 프로젝트(핵심 포함)** | 학교마다 Supabase 프로젝트 하나에 핵심 + 앱 칸 | 높음 | **강함** | ~$25 + $10×100 = **~$1,025** | **~$10,000+** | 높음. 마이그레이션·기본판 갱신·감시를 N번 |
| **4. 계층형 (추천)** | 핵심은 공용(지금). **확장을 켠 학교만** 전용 Supabase 프로젝트 1개를 받고, 그 안에 앱 칸을 둔다(포털식). 앱마다 Vercel 프로젝트. 핵심과는 OIDC + API 창구로만 주고받음 | 높음(확장 학교) | 핵심: RLS·검증된 우리 코드. 확장: 학교 단위로 물리 격리 | ~$60~110 + $10×20 = **~$260~310** | ~$200~500 + $10×200 = **~$2,200~2,500** | 중간. N은 '확장 켠 학교'만, 핵심 마이그레이션은 한 번 |

- 3안의 1,000곳 비용은 Micro 컴퓨트만 넣은 하한이다. 학교가 커지면 Small($15) 이상이 된다.
- 4안은 확장 비용을 그 학교 요금에 붙일 수 있다(예: '확장형' 요금에 월 $10~15 원가 포함). 그래서 플랫폼 원가가 쓰는 학교만큼만 늘어난다.
- 4안에서 큰 학교나 법적으로 격리가 필요한 학교는 **핵심까지 전용 프로젝트로 옮기는 '전용형'**을 줄 수 있다. ADR 0019 단계 D '셀 나누기'의 셀 크기 1이다. 모든 표에 `school_id`와 복합 외래키가 있어서 가능하다.

## 5. 추천 [판단]: 4안 계층형

**이유**
1. **목적 충족**: 확장을 켠 학교는 학교 AI가 자기 표(선언)·서버 코드·외부 연동을 자유롭게 만든다. 포털처럼 앱마다 백엔드가 나뉘어 충돌하지 않는다.
2. **기록 보존**: 학적·성적 마감 판·발행본 해시·열람 계정 같은 '틀리면 안 되는 기록'은 RLS와 판 규칙이 지키는 공용 핵심에 남는다. 학교 AI 코드가 이 표에 닿지 않는다.
3. **위험 범위**: 학교 AI 코드의 실수(RLS 누락·나쁜 질의)는 그 학교 확장 프로젝트 안에 갇힌다. 포털이 경고한 '한 그릇' 위험을 핵심에서 피한다.
4. **비용·관리**: 원가와 관리 대상(N)이 '확장을 켠 학교 수'에만 비례한다. 핵심 마이그레이션은 지금처럼 한 번이다. 77~79차 Actions 문을 그대로 쓴다.
5. **포털 권고와 같은 방향**: 학교 경계는 프로젝트로, 앱 칸은 학교 안에서만.

**반대 근거·남는 위험**
- 핵심 공용 DB의 '한 학교만 복원 불가'와 '시끄러운 이웃' 문제는 남는다.
  - 대응: 학교 떼어 내기(A5), 공개 페이지 캐시(A2), 필요한 학교의 전용형 이전
- 확장 프로젝트에 학생 개인정보가 복사되면 보존·삭제 요청 대응이 흩어진다.
  - 규칙 후보: 확장에는 person id만 두고, 이름·성적은 API 창구로 그때그때 읽는다. 복사 저장은 금지한다.
- 학교 확장 프로젝트를 만들고 지우는 일을 자동화해야 한다.
  - Supabase 관리 API로 프로젝트를 만들 수 있는 것으로 안다 [확인 필요].
  - 프로젝트마다 생기는 키를 안전하게 보관할 곳이 필요하다. 포털은 DB 안 KV 표에 암호화해 둔다.
- 사람 일이 는다: 확장 학교 수만큼 감시(느린 질의·용량)가 늘어난다. 관제 보고 계약(`school_report_v1`)에 확장 사용량 칸을 더하는 식으로 모은다.
- Supabase 조직당 프로젝트 수 한도가 있는지 [확인 필요].

## 6. 4안을 택하면 바뀌는 것 (구현 순서 제안)

1. **ADR 0035(예정, 0034는 89차 템플릿 완성 디자인이 씀)**: 계층형 백엔드(기본형·확장형·전용형).
   - ADR 0025 '에이전트 DDL·코드 업로드 없음'을 고친다: 핵심에는 여전히 없고, 확장 프로젝트에서는 선언 표 + 코드 배포를 허용한다.
   - ADR 0019 '학교마다 Supabase 프로젝트 기각'을 고친다: 확장·전용형에 한해 허용한다.
2. **onschools를 OIDC 제공자로**: 학교 앱이 'onschools로 로그인'으로 붙는다.
3. **공용 API 창구**: `/api/platform/*` + 학교·앱별 허용목록 + `usage_events` 장부. 기존 범위 토큰을 넓히는 방향이다.
4. **확장 프로비저닝**(관리자 승인 한 번)
   - Supabase 프로젝트, 앱 칸, GitHub 템플릿 저장소, Vercel 프로젝트, 환경 변수, 서브도메인
   - 포털의 `provisionBackend`·`createRepoFromTemplate`·`setVercelEnvVars` 흐름을 참고하되, 코드를 복사하지 않고 이 저장소에서 새로 짠다(ADR 0026 독립 원칙).
5. **선언 표**(`tables.json`) 검사기: 이름공간, RLS 필수, 핵심 개인정보 칸 금지
6. **확장형 요금**(라이선스 항목) + 사용량 상한

## 7. 결정해 주실 것
- 4안(계층형)으로 갈지, 3안(전 학교 전용 프로젝트)이나 1안(지금 유지)으로 갈지
- 4안이면 첫 단계를 ADR 0035 + OIDC·API 창구부터 할지, 확장 프로비저닝 시범(드리미학교 1곳)부터 할지

## 8. 포털의 덧붙임과 바로 한 일 (2026-11-26)
- 포털: "포털이 위험한 까닭은 DB를 공유해서가 아니라 공유 DB에 **두 번째 담이 없어서**다. 모든 표 RLS를 지키면 걱정의 대부분이 사라진다. 다만 지키기 어려우니 **정책 없는 표가 생기면 배포를 세우는 문**을 처음부터 두라. 핵심 쪽의 시끄러운 이웃·한 학교 복원 문제는 학교 수가 아니라 **가장 무거운 한 학교**가 정한다. 평균 말고 최대를 보라."
- 잰 값 [잼]
  - 테스트 DB 기준: public 표는 모두 RLS가 켜져 있다.
  - `school_id`가 있는 표는 모두 정책이 있다.
  - 그냥 `true`인 정책은 내부 역할(`control_writer`)용이거나 공개 기능 목록 하나뿐이다.
  - 비공개 스키마에는 사람·에이전트 권한이 없다.
- 한 일(80차): `tests/rls-gate.test.ts`. 위 조건이 깨지면 CI가 실패한다. 79차부터 운영 배포가 main CI 뒤에만 서므로 이 시험이 곧 배포를 세우는 문이다.
- 남은 일: 관제 보고에 '가장 무거운 학교'(행 수·질의 시간 최대) 칸을 더하는 것. A3(DB 연결)·A2(공개 캐시)와 함께 한다.
