# UI 점검 루프 (Claude 구현 → Codex 점검 → Claude 개선)

> 위치: `docs/UI_REVIEW.md`. UI 점검에 관한 규칙은 이 문서 한 곳에만 둔다(ADR 0033).
> `CLAUDE.md`·`AGENTS.md`에는 맨 아래 "연결 문구"만 넣는다.
> 원본은 선생님이 드리미포털용으로 정리한 문서다(2026-11-26). 이 저장소에 맞게 바꾼 곳은 각 절에 [학교 플랫폼]으로 표시했다.

> **요약** Claude가 화면을 만들면 스크립트가 화면을 찍고 기계 검사를 한다. 그다음 Codex가 체크리스트로 점검하고, Claude가 지적을 골라 고친다.

> **왜** 에이전트는 코드를 쓰지만 렌더된 화면을 보지 못한다. 겹침, 묻힌 버튼, 어색한 여백은 코드만으로는 드러나지 않는다. 만든 쪽이 스스로 채점하면 후하므로 점검은 다른 모델이 한다.

**용어 풀이**

| 용어 | 쉬운 설명 | 예시 |
|---|---|---|
| 렌더 | 코드가 브라우저에서 실제 화면으로 그려지는 것 | 같은 코드도 휴대폰에서는 글자가 잘릴 수 있음 |
| 뷰포트 | 화면을 보는 창의 크기 | 390px = 휴대폰, 768px = 태블릿, 1440px = 데스크톱 |
| axe | 접근성(글자 대비·레이블·대체 글) 자동 검사 도구 | 흐린 회색 글자가 배경과 구분되지 않으면 잡음 |
| 린트 | 코드에서 규칙 위반을 자동으로 찾는 검사 | 정해진 색 토큰 대신 #fff 같은 색을 직접 쓰면 잡음 |
| 디자인 토큰 | 색·간격·글자 크기를 이름으로 정해 둔 값 | var(--text-muted) = '흐린 글자색' |
| 기준 이미지 | '이게 맞는 화면'으로 저장해 둔 그림. 이후 화면과 픽셀을 비교함 | 의도치 않게 바뀐 여백을 잡음 |

## 1. 왜 하는가
- 에이전트는 렌더된 화면을 보지 못한다. 겹침, 묻힌 버튼, 어색한 여백은 코드만으로는 드러나지 않는다.
- "직관적으로"는 검사할 수 없다. 기준을 체크리스트(5장)로 고정해야 점검할 수 있다.
- 만든 쪽이 스스로 채점하면 후하다. 그래서 구현(Claude)과 점검(Codex)을 나눈다.

## 2. 역할
| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| Claude Code | 구현, 스크린샷 캡처, 기계 검사, 지적 선별, 수정 | 자기 화면을 스스로 "통과" 처리 |
| Codex | 스크린샷과 체크리스트로 점검, 개선 제안 | 코드 수정(읽기 전용) |
| 사람 | 단계 끝에서 결과 확인, 기준 화면 승인 | 페이지마다 눈으로 확인 |

## 3. 언제 돌리는가
- UI에 영향을 주는 변경(페이지, 컴포넌트, 스타일)을 마쳤을 때, **변경된 페이지만** 대상으로 한다.
- 전 페이지 일괄 점검은 사용자가 요청할 때만 한다(Codex 호출량이 크다).
- 문구만 바뀐 변경, 서버 로직만 바뀐 변경은 건너뛴다.

## 4. 절차
1. **4-1 캡처** — 3뷰포트 × 상태 (Claude, 스크립트)
2. **4-2 기계 검사** — 콘솔·가로 스크롤·axe·색 린트 (모델 호출 없음)
3. **4-3 Codex 점검** — 체크리스트·출력 형식 (읽기 전용)
4. **4-4 선별·수정** — 수용·기각·보류 (Claude)
5. **4-5 재점검·종료** — 최대 2회 · 기준 이미지

### 4-1. 캡처 (Claude) [학교 플랫폼: 스크립트로]
로컬 서버(로컬 DB + 합성 시드)를 띄운 뒤 스크립트로 찍는다.
```bash
npm run db:reset && npm run build && npx next start -p 3000   # 또는 npm run dev
npm run ui:review -- lab attendance        # 페이지 이름들(목록: scripts/ui-review.pages.mjs)
```
- 뷰포트 3종: 390×844, 768×1024, 1440×900
- 상태 4종(기본 `default`·빈 상태 `empty`·데이터 많음 `many`·오류 `error`) 가운데 해당하는 것만 쓴다. 페이지별 상태와 경로는 `scripts/ui-review.pages.mjs`에서 정한다.
- 결과: `.ui-review/<페이지>/<상태>-<뷰포트너비>.png` + `machine.md`(기계 검사 결과). `.ui-review/`는 커밋하지 않는다(.gitignore).
- 로그인은 로컬 시드의 **합성 예시 계정**으로만 한다. 운영 주소는 기본으로 막혀 있다.

### 4-2. 기계 검사 (Codex 호출 전에 반드시 통과)
아래가 하나라도 있으면 먼저 고치고 다시 캡처한다. 이 단계는 모델을 부르지 않는다.
- 콘솔 오류, 가로 스크롤(`scrollWidth > clientWidth`), axe serious 이상 위반: `npm run ui:review`가 잡는다. 하나라도 있으면 종료 코드 1이다.
- 디자인 토큰 밖 색상값·인라인 px: `npm run lint:colors`가 잡는다. CI에서도 돈다.
  - 지금 있는 것(24개, 대부분 인쇄용 종이·무지개 장식·Google 단추 브랜드 색)은 기준 목록 `scripts/lint-colors.baseline.json`으로 묶었다. **새로 생긴 것만** 실패로 본다.
  - 목록은 줄이기만 한다.
- [학교 플랫폼] 전체 흐름 e2e(`npm run test:e2e`)도 화면을 찍을 때마다 axe를 돌린다.

### 4-3. 점검 (Codex, 읽기 전용) [학교 플랫폼: 돌릴 곳 세 가지]
| 어디서 | 방법 | 비용 | 화면(스크린샷)을 보나 |
|---|---|---|---|
| **선생님 Mac의 Codex CLI** (기본) | 아래 명령. 캡처는 Mac에서 4-1로 하거나 `.ui-review`를 받아 온다 | ChatGPT 요금제 사용량(`codex login` 상태에 따름) | 예 |
| **Codex GitHub 코드 리뷰** (PR 자동, 2026-11-27 연결 확인) | Codex 설정에서 이 저장소 코드 리뷰를 켜거나 PR에 `@codex review`. AGENTS.md의 리뷰 규칙을 따른다 | ChatGPT 구독(요금제별 포함 여부는 확인 필요) | 아니오(코드만). 화면 점검은 별도 지시가 필요하고, 클라우드 환경에서 캡처가 되는지는 시험 전 |
| Codex GitHub Action (`openai/codex-action`) | CI에서 `codex exec` | **OpenAI API 키(사용량 과금)** | 예 |

- 세 번째는 ADR 0032(AI는 구독 계정으로, 유료 API 기본 안 씀)와 부딪친다. 비용 추정과 선생님 확인 없이 쓰지 않는다.
- 이 클라우드 작업 환경(Claude 세션)에는 Codex가 없다.

```bash
PAGE=lab   # 점검할 페이지 이름
SHOTS=$(ls .ui-review/$PAGE/*.png | paste -sd, -)
codex exec \
  "docs/UI_REVIEW.md의 5장 체크리스트와 6장 출력 형식을 따라 첨부한 화면을 점검하라. \
대상 페이지: $PAGE. 파일명은 <상태>-<뷰포트너비>.png 이다. 기계 검사 결과는 .ui-review/$PAGE/machine.md 에 있다. \
필요하면 해당 페이지의 소스와 docs/design/DESIGN-SYSTEM.md, src/app/globals.css 의 토큰을 읽어 근거를 확인하라. \
코드는 수정하지 말고 제안만 하라." \
  --sandbox read-only \
  -i "$SHOTS" \
  -o .ui-review/$PAGE/review.md
```
- 플래그 순서와 `-i` 동작은 설치된 버전에서 `codex exec --help`로 한 번 확인한다(미검증).
- 한 번에 이미지가 너무 많으면 뷰포트별로 나눠 호출한다.

### 4-4. 선별과 수정 (Claude)
GitHub 리뷰로 받은 지적은 같은 판정을 PR 답글로 남긴다(`docs/COLLABORATION.md` 8절).
`review.md`의 지적을 모두 그대로 받아들이지 않는다. 항목마다 아래 중 하나로 판정하고 같은 폴더의 `triage.md`에 적는다.
- **수용**: 체크리스트 항목에 근거가 있고 화면에서 확인된다 → 수정한다.
- **기각**: 저장소 UI 규약(디자인 토큰, `docs/design/DESIGN-SYSTEM.md`)과 충돌하거나 체크리스트 근거가 없는 취향 의견이다 → 이유를 한 줄 적는다.
- **보류**: 범위가 크거나 설계 결정이 필요하다 → 사용자에게 선택지로 올린다.

규약과 Codex 제안이 부딪히면 규약이 이긴다. 규약 자체가 틀렸다고 판단되면 규약 문서를 고치는 안을 사용자에게 올린다(우회해서 예외를 만들지 않는다).

### 4-5. 재점검과 종료
- 수정 후 4-1, 4-2를 다시 하고, 수용한 "높음" 항목이 있었을 때만 4-3을 한 번 더 한다.
- Codex 점검은 페이지당 **최대 2회**. 2회 뒤에도 "높음"이 남으면 멈추고 사용자에게 보고한다.
- 종료 시 기준 이미지를 저장해 이후 의도치 않은 변화를 픽셀 비교로 잡는다(모델 호출 없음). [학교 플랫폼] e2e가 Playwright 테스트 도구(`@playwright/test`)가 아니라 자체 스크립트라 `toHaveScreenshot`이 없다. 기준 이미지 비교는 **아직 없음**(다음 단계 후보).

## 5. 체크리스트
각 항목은 통과/실패로 판정한다. 근거는 화면에서 보이는 것으로만 댄다.

**A. 위계와 명료성**
- A1. 화면의 주요 행동이 하나이고, 가장 눈에 띈다.
- A2. 제목만 읽어도 이 화면이 무엇을 하는 곳인지 안다.
- A3. 정보가 중요도 순으로 배치되어 있다(중요한 것이 위, 크게).
- A4. 한 화면에 강조색이 과하지 않다(강조는 주요 행동과 상태 표시에만).

**B. 일관성**
- B1. 간격, 글자 크기, 모서리 반경이 토큰 단계에 맞는다.
- B2. 같은 역할의 요소가 다른 페이지와 같은 모양·위치다(버튼, 표, 폼, 탐색).
- B3. 용어가 통일되어 있다(같은 동작에 다른 낱말을 쓰지 않는다).

**C. 상태와 피드백**
- C1. 빈 상태에 "왜 비었는지"와 "다음에 할 일"이 있다.
- C2. 로딩, 오류, 성공 상태가 각각 표시된다.
- C3. 오류 문구가 원인과 해결 방법을 말한다.
- C4. 되돌릴 수 없는 행동에는 확인 단계가 있다.

**D. 반응형과 가독성**
- D1. 390px에서 가로 스크롤, 잘린 글자, 겹침이 없다.
- D2. 터치 대상이 44px 이상이다.
- D3. 긴 한글 텍스트가 어색하게 줄바꿈되거나 넘치지 않는다.
- D4. 본문 대비가 충분하다(WCAG AA).

**E. 폼과 입력**
- E1. 모든 입력에 보이는 레이블이 있다(placeholder만으로 대체하지 않는다).
- E2. 필수 항목과 형식 안내가 입력 전에 보인다.
- E3. 입력 순서가 사용자의 작업 순서와 같다.

## 6. Codex 출력 형식
```markdown
## 요약
- 통과 n / 실패 n, 가장 급한 것 한 줄

## 지적
| 번호 | 심각도 | 항목 | 화면(파일명) | 보이는 현상 | 제안 |
|---|---|---|---|---|---|
| 1 | 높음 | C1 | empty-390.png | 빈 목록에 안내 문구 없음 | 안내 문구와 추가 버튼 배치 |

## 확인하지 못한 것
- 스크린샷으로 판단할 수 없었던 항목 (예: 로딩 상태 화면 없음)
```
- 심각도: **높음**(작업을 못 하거나 헷갈린다) / **중간**(불편하다) / **낮음**(다듬기).
- 체크리스트 항목 번호가 없는 지적은 쓰지 않는다. 꼭 필요하면 "항목 외"로 표시하고 이유를 적는다.
- 새 색상, 새 서체, 새 컴포넌트 도입은 제안하지 않는다. 기존 토큰과 컴포넌트 안에서 제안한다.
- 추측("사용자가 헷갈릴 것 같다")은 화면에서 보이는 근거와 함께 적는다.

## 7. 비용과 한계
- Codex 호출은 ChatGPT 요금제 사용량 또는 API 과금을 쓴다. 어느 쪽인지는 `codex login` 상태에 따른다. API 키 과금이라면 첫 실행 전에 사용자에게 확인한다(ADR 0032).
- 비용을 줄이는 순서: 변경된 페이지만 → 기계 검사 먼저 → 점검 최대 2회.
- 이 루프는 정렬, 위계, 일관성, 누락된 상태를 잘 잡는다. "실제 사용자가 헤매는가"는 잡지 못한다. 새 모듈을 열 때는 사용자 3~5명에게 과제를 주고 관찰하는 것을 따로 한다.

## 8. 보고 (Claude, 작업 종료 시)
- 점검한 페이지와 횟수
- 수용해서 고친 것 / 기각한 것과 이유 / 보류해서 사용자 결정이 필요한 것
- 확인하지 못한 것(찍지 못한 상태, 실행하지 못한 검사)
- 보고는 AGENTS.md '선생님께 설명할 때' 순서(요약 → 왜 → 용어 풀이)를 따른다.

```markdown
## UI 점검
UI 점검 요청을 받으면 `docs/UI_REVIEW.md`의 5장 체크리스트와 6장 출력 형식을 따른다. 점검 시에는 코드를 수정하지 않는다.
```
