# 0036. 학교 홈페이지 방문·상담 신청 — 방문자가 남기는 첫 쓰기 경로

- 상태: 채택
- 날짜: 2026-11-27
- 제안: Claude(홈페이지 세션)
- 결정: 사용자(2026-11-27, "방문·상담 신청 폼 → 폼까지 만들기"). 설계안은 관제 센터 결정 요청 #24로 올렸다. 되돌릴 수 있는 일이라 추천안(A)으로 진행했다.
- 번호: 0035는 계층형 백엔드에 예약되어 있다(#138).

## 배경
- 상용 학교 템플릿은 대부분 방문·상담 신청을 둔다(`docs/design/homepage-commercial-plan.md` 4절 ⑧).
- 지금까지 방문자는 공개된 판을 **읽기만** 했다. 신청은 방문자(로그인 없음)가 학교 자료를 **만드는** 첫 길이다. 그리고 이름·연락처라는 개인정보를 받는다.

## 고려한 안
| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A 검사 함수 하나로만 쓰기(채택)** | 방문자는 표 권한 없음. `app.submit_site_inquiry`(security definer)가 열린 홈페이지·신청 받기·동의·횟수를 검사하고 넣음 | 쓰기 경로가 하나, DB가 규칙을 지킴 | 함수가 커짐 |
| B anon에 insert 정책 | 표에 anon insert 정책 | 단순 | 정책 실수 하나로 다른 학교 칸에 쓰거나 읽힐 위험, RLS 문(80차)과도 맞지 않음 |
| C 안내·연락 링크만 | 전화·메일 링크 | 개인정보를 받지 않음 | 사용자 결정과 다름 |

## 결정
- **A를 채택한다.**
- 표 `site_inquiries`
  - 칸: `school_id`, 종류(방문·상담·문의), 이름, 연락처, 희망 날짜, 남긴 말, 언어, 쪽, 동의 시각, 상태, 가린 시각
  - 길이 제약을 둔다.
  - RLS: 읽기·고치기는 `app.is_member(school_id) and app.is_school_admin(school_id)`(그 학교 관리자 + 전체 관리자). 교사·학생·보호자 열람 계정·다른 학교는 볼 수 없다.
  - 사람이 고칠 수 있는 칸은 처리 상태뿐이다(열 단위 권한). 지우기 권한은 없다.
- 학교 ID는 주소 이름(slug)으로 DB 함수가 정한다. 클라이언트가 보낸 학교 ID는 받지 않는다.
- 학교가 고르는 것
  - 설정의 '방문·상담 신청 받기'(`site_settings.inquiry_open`, 기본 꺼짐)
  - 쪽에 넣는 '방문·상담 신청' 블록. 둘 다 있어야 방문자에게 보인다.
- 스팸·남용 막기
  - 동의 필수(DB 검사)
  - 같은 연락처는 하루 3건, 학교당 한 시간 30건
  - 사람에게 안 보이는 칸이 채워지면 저장하지 않는다.
  - 같은 출처 요청만 받는다.
- 보존
  - 관리자가 보존 기간(30일 이상, 화면 기본 365일)을 정해 '가리기'를 누른다. 그보다 오래된 신청의 이름·연락처·남긴 말·희망 날짜를 가린다.
  - 행과 받은 날·종류는 남고, 활동 기록을 남긴다(ADR 0028 방식, 지우지 않음).
- 앱 경로
  - 방문자 요청은 새 도우미 `asVisitor`(anon, 쓰기 가능한 트랜잭션) 안에서 위 함수만 부른다.
  - 사용자 요청은 그대로 `asUser`다.
- 템플릿: 유치원형 입학 쪽, 입학 모집형 입학 쪽에 신청 블록을 넣는다. 학교가 켜기 전에는 방문자에게 보이지 않는다.
