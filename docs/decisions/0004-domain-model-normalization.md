# 0004. 도메인 모델 정규화: 학교 · 사람 · 학사 구조 · 수업 · 평가 · 발행

- 상태: **제안** (Claude 안 A · Codex 안 B) — 비교 후 사용자가 결정
- 날짜: 2026-11-22
- 제안: Claude (안 A, 관제 세션) · Codex (안 B)
- 근거: [드리미포털 구조 분석](../research/portal-analysis.md) L1~L13, 14~17차 구현, ADR 0001~0003
- 결정: 사용자 (대기)

## 배경

새 플랫폼은 지금 학사 규칙 확정과 문서 발행(14~16차)까지만 있다. 학생부 · 학생 포털 · 학교 홈페이지를 올리려면 사람·학기·수업·평가의 핵심 표가 필요하다. 드리미포털은 학교 개념 없음, 사람을 문자열로 참조(180열), 통계 모집단을 과목명으로 묶음, 규칙 사본 같은 구조 문제로 사고가 반복됐다. 처음부터 정규화된 핵심 모델을 세운다.

## 안 A: 핵심 표 (Claude)

```
schools ─┬─ school_settings (판)            school_levels (중·고 …)
         ├─ academic_years ── terms (학기·텀; 14차 확정 규칙에서 생성)
         ├─ cohorts (기수: 입학 학년도·학교급) ── homerooms (반, 학년도별)
         ├─ people ── person_names (이름 이력) ── person_accounts (계정 연결, 0..n)
         │     └─ enrollments_school (학적: 입학·전학·졸업·상태, 기간)
         ├─ subjects (실제 과목) ── subject_labels (발행 표기, 판·적용 범위)
         ├─ course_types (갈래: 수명주기 계기·공개 규칙·P/F 허용)
         ├─ course_offerings (학기·과목·갈래·블록·학교급·학점·P/F)
         │     ├─ offering_staff (person, 역할: 담당·보조·외부 강사)
         │     ├─ offering_enrollments (person, 상태, P/F 선택)
         │     ├─ assessments (평가 항목) ── assessment_results (원점수·성취도·P/F)
         │     ├─ narratives (세특 등 서술, 글자 한도는 school_settings)
         │     └─ population_exclusions (모집단 제외 person·사유)
         ├─ record_items (출결·수상·자격·동아리·행동특성 등, 종류 표 + 값)
         └─ published_documents (14차) ← 스냅샷에 과목 표기 판·통계·양식 포함
```

- **권한**: 역할(학교 관리자·교사)은 `memberships`(16차). 모듈 단위 관리자 `module_grants(person/account, module, 범위)`. 수업 단위 권한은 `offering_staff`에서 유도(담당 교사만 그 수업 성적 저장).
- **학생 포털**: 학생·보호자 계정은 `person_accounts`로 자기 `person`에만 연결, RLS 규칙 "본인 기록만".
- **홈페이지**: `site_pages`·`site_blocks`(판·공개 상태), 공개 수업 아카이브는 `course_offerings` + `course_types.publishable`에서 만드는 **뷰**(사본 금지).
- **통계**: `offering_stats(offering_id, mean, sd, n, computed_at)`는 계산 결과 캐시일 뿐이고, 발행본에는 그때 값을 스냅샷으로 넣는다. 표기 변경은 모집단에 영향이 없다(키가 id).

## 안 B (Codex)

### B1. 업무별 쓰기 경계 + 성적 마감 판 + 용도별 조회

**제안:** 한 앱·한 PostgreSQL DB와 정규화된 공통 핵심을 유지하되, 학적·수업 운영·학생부·발행의 **쓰기 책임을 나누고**, 확정된 성적·모집단·통계를 수업별 불변 마감 판으로 만든다. 학생 포털은 허용된 조회 모델을, 발행기는 선택한 마감 판을 읽는다. 아래 표·함수 이름은 구현 계약을 설명하는 가칭이다.

안 A의 중심은 공통 핵심 표와 수업별 통계 캐시, 발행 시 스냅샷이다. 안 B는 여기에 **발행과 독립된 업무 확정 단위**를 둔다. 예를 들어 같은 수업의 국문 학생부와 대학 제출용 문서가 표기를 달리해도 같은 마감 판의 모집단·성적을 사용한다. 성적 정정 때는 새 마감 판을 승인하고, 기존 발행본을 자동 갱신하지 않는다.

읽기·쓰기 로직을 같은 저장소 안에서 분리하는 방식은 Microsoft의 기본 CQRS 설명에 근거한다[S1]. 여기서는 메시지 브로커나 별도 DB를 도입하지 않는다. 전면 이벤트 소싱은 재생·이벤트 스키마 진화·운영 복잡도를 더하므로[S2], 현재 관계형 상태와 확정 판을 원장으로 삼는다. 변경 이력은 감사용이며 이를 재생해야만 현재 상태를 읽을 수 있게 만들지 않는다. 이는 출처의 제품 권고가 아니라 이 프로젝트에 대한 **설계 판단**이다.

### B2. 데이터와 수정 책임

모든 학교 소속 표(연결·감사·판·조회용 저장 표 포함)에 `school_id NOT NULL`을 둔다. 아래 묶음은 논리적인 업무 경계이며 학교마다 DB·스키마를 새로 만들지 않는다.

| 소유 업무 | 표와 관계(안 A에서 유지하거나 구체화) | 쓰기 계약 |
| --- | --- | --- |
| 공통 신원·학사 | `people → person_names`, `person_accounts`, `school_levels → academic_years → terms`, `cohorts`, `homerooms`, 기간이 있는 `enrollments_school`·반 배정 | 사람은 학교별 id로 관리하고 자동으로 학교 간 병합하지 않는다. 계정은 기존 `private.app_users`에 연결한다. `terms`는 확정 `school_rules` 판을 FK로 참조하며 규칙 변경으로 기존 수업의 학기를 조용히 재작성하지 않는다 |
| 수업 운영 | `subjects`, `course_types`와 그 규칙 판, `course_offerings → offering_staff / offering_enrollments` | 개설·배정·수강 변경 명령이 상태 전환을 검증한다. 갈래의 생성 계기·공개 가능 여부·P/F 허용은 규칙 판 한 곳에서만 읽고 수업은 적용 판을 고정한다 |
| 평가·학생부 | `assessments → assessment_results`, `narratives`, `population_exclusions`, `offering_closures → closure_members / closure_results / closure_stats` | 담당 교사는 초안을 수정한다. 승인된 마감 판과 그 자식 행은 추가만 허용한다. 출결·수상 등은 종류별 형식 표와 FK를 두고, 임의 JSON 안에 사람·수업 참조를 숨기지 않는다 |
| 표기·발행 | `subject_labels`(과목·학년도·용도·판), 기존 `published_documents`, 신규 `document_closures`·`document_label_versions` | 발행 명령만 마감 판·표기 판·양식 판을 조합한다. 새 발행본과 연결 행은 한 트랜잭션으로 만든다. 기존 발행본에 연결 행을 소급 삽입하거나 스냅샷을 수정하지 않는다 |
| 포털·홈페이지 | 학생별 허용 열 조회, 홈페이지 편집 판, 승인된 내보내기 스냅샷 | 포털은 원장의 성적을 직접 수정하지 않는다. 홈페이지 공개 자료는 허용 필드만 투영한 승인 판에서 생성한다 |

- **FK 계약(P1·P9):** 학교 소속 부모에 `UNIQUE(id, school_id)`, 자식에 `FOREIGN KEY(parent_id, school_id)`를 둔다. 마감 판·학생·수강의 일치도 학교 FK만으로 끝내지 않고, `(school_id, closure_id, offering_id)`와 `(school_id, offering_id, enrollment_id)`처럼 필요한 조합을 UNIQUE/FK로 연결한다. 같은 학교의 다른 수업 성적을 섞는 경우도 거부해야 한다[S3].
- **계정 연결(P2·P3):** 한 학교에서 계정 하나는 사람 하나에만 연결하고 사람 하나는 계정 0..n개를 가진다. `person_accounts`는 사람 복합 FK와 `memberships(user_id, school_id)` 복합 FK를 가진다. 이름·메일이 같다는 이유로 연결하지 않는다. 탈퇴는 접근을 철회하되 성적의 사람 id는 보존한다. 연결 철회 이력은 별도로 남긴다.
- **설정(P4·P7·P8):** 학교급·기수·반·학기를 id로 표현하고 조회 계약에 학교급을 필수로 둔다. `school_settings`의 승인 판이 글자 한도·계산 규칙을 소유하고 갈래 규칙 판이 수명주기를 소유한다. 같은 설정 값을 양쪽에 복제하지 않는다. 새로운 자료와 승인 규칙이 충돌하면 질문을 열고, 적용 판 변경은 명시적으로 승인한다.

### B3. 마감·정정·발행의 일관성

1. **초안 저장:** 모든 수강·평가·제외 변경은 해당 수업의 행을 잠그고 상태 및 예상 revision을 검사한다. 허용된 변경과 감사 기록을 같은 트랜잭션에 쓰고 커밋까지 기다린다. 다른 편집이 먼저 저장됐으면 충돌로 응답한다.
2. **마감:** 같은 수업 잠금을 획득한 뒤 수강 명단, 포함·제외 사유, 점수·P/F, 서술, 규칙 판을 읽는다. `offering_closures`에 `offering_id`, 판 번호, 승인자 계정 FK, 확정 시각, 규칙 판 FK를 두고, 자식 표에 당시 모집단과 성적 및 평균·표준편차·n을 함께 저장한다. 모든 관련 쓰기 경로가 동일 잠금을 지키고 마감 후 초안 변경을 거부해야 한다. 현재 `asUser()`의 일반 트랜잭션만으로 여러 질의가 같은 시점을 본다고 가정하지 않는다[S6·R2].
3. **중복·부분 실패:** 마감 요청에는 학교·수업 범위의 고유 요청 키를 둔다. 동일 요청 재시도는 기존 결과를 돌려주고, 같은 키의 다른 입력은 거부한다. 성적·모집단·통계·감사 기록 중 하나라도 실패하면 전체를 롤백한다. 권한 실패·입력 오류·편집 충돌·운영 장애를 구별하고 DB 오류나 사용자 입력 원문을 그대로 노출하지 않는다.
4. **정정:** 사유와 이전 판 FK를 가진 새 마감 판을 만든다. 정정 초안은 이전 확정 결과에서 시작할 수 있지만 확정 판 자체는 수정·삭제하지 않는다. 한 이전 판에서 두 후속 확정 판이 갈라지지 않도록 유일 제약과 잠금을 둔다. 정정 승인 권한과 반려 흐름은 **확인 필요**.
5. **발행:** 선택한 마감 판의 성적·통계를 복사하고, 별도로 선택한 해당 과목의 학년도·용도별 표기 판, 이름 표기, 규칙·양식·가리기 정책의 판을 스냅샷에 담는다. 발행 화면은 저장된 스냅샷만 렌더링한다. 마감 판 참조와 표기 판 참조는 관계형 연결 표의 FK로 보장하며, JSON 내 id만으로 관계를 대신하지 않는다. 이는 기존 14차 발행 보존 구조를 확장하는 제안이다[R2].
6. **내보내기:** 외부용 스냅샷은 허용 필드 목록으로 새로 구성한다. 사진·이름을 화면에서 숨기기만 하지 않고, props·메타데이터·원본 첨부에도 허용하지 않은 값이 없는지 검사한다. 내부 원장·기존 발행본은 그대로 보존한다.

통계의 키는 끝까지 `offering_id`이고 `closure_id`는 **그 모집단을 어느 시점에 확정했는지**를 식별한다(P6). 표기명은 계산 키가 아니다. P/F·결시·전출·제외자의 분모 처리, 표본/모집단 표준편차, 반올림, 소규모 집단의 공개 기준은 **확인 필요**이며 학교별 승인 규칙으로 정해야 한다. 마감 판은 승인된 사실의 사본이고, 계산·공개 규칙의 별도 원본을 만드는 것이 아니다.

### B4. 권한과 공개 경계

- **사용자 요청:** 기존 `asUser()`와 JWT 사용자 맥락을 유지한다. 학교는 로그인 사용자의 검증된 소속에서 정한다. 모든 학교 표의 읽기 `USING`과 쓰기 `WITH CHECK`에서 `app.is_member(school_id)`를 기본 조건으로 쓰고, 업무 역할·담당 수업·본인 범위를 **추가**로 검사한다. `asSystem()`이나 서비스 키를 업무 쓰기의 우회로로 쓰지 않는다.
- **DB가 강제하는 쓰기 경계:** 신규 업무 표의 직접 DML 권한을 요청 역할에서 회수하고 개설·저장·마감·발행 명령 함수의 실행만 허용한다. 필요한 `SECURITY DEFINER` 함수는 로그인·`BYPASSRLS`·슈퍼유저 권한이 없는 제한 소유 역할로 실행하고, 해당 역할에도 RLS를 적용한다(표 소유자라면 `FORCE ROW LEVEL SECURITY`). 안전한 `search_path`, 정규화한 객체 이름, `PUBLIC` 실행 권한 회수, 호출 사용자·학교·업무 권한 재검증을 함께 설계한다[S4·S5]. 함수 소유 역할을 요청 역할이 `SET ROLE`로 획득할 수 없어야 한다. 기존 함수의 권한을 이 PR에서 일괄 변경하지 않으며 관리형 DB에서의 역할 생성·소유권 적용은 **확인 필요**.
- **조회:** 내부 조회 뷰는 호출자 권한과 RLS를 적용하는 `security_invoker`를 사용하고, 허용할 열도 제한한다[S7]. 뷰만으로 기초 표의 접근을 안전하게 만들었다고 간주하지 않는다. 확정 판의 UPDATE·DELETE·TRUNCATE를 차단하고, 확정 후 자식 행 추가도 DB에서 거부한다.
- **학생·보호자:** 학생은 자기 사람 id에 연결한다. 보호자는 **보호자 자신의 사람 id**에 연결하고, 별도 `guardian_links(school_id, guardian_person_id, student_person_id, 유효기간, 허용범위)`와 양쪽 사람 복합 FK로 자녀 접근을 검증한다. 학생 계정을 보호자와 공유하거나 보호자 계정을 학생 person에 연결하지 않는다. 관계 확인·동의·철회 기준은 **확인 필요**다.
- **기존 권한과의 접점:** 현재 `memberships`의 역할은 admin·teacher이고, 여러 기존 읽기 정책은 학교 소속만 검사한다[R3]. 학생·보호자 역할만 추가하면 학교 전체 문서·구성원이 노출될 수 있으므로, 해당 계정 도입 전에 기존 표까지 포함한 정책 행렬과 양방향 거부 시험이 필수다. 좌석 계산·초대·라이선스에 이 역할을 포함할지도 **확인 필요**다.
- **홈페이지:** P1과 독립 인프라 원칙을 유지해 익명 브라우저가 학교 원장이나 내부 뷰를 직접 읽게 하지 않는다. 갈래 규칙상 공개 가능한 후보를 담당자가 승인한 뒤, 허용 필드만 담긴 내보내기 스냅샷으로 정적 공개 산출물을 생성하는 방향을 제안한다. 생성 요청도 권한 있는 사용자의 `asUser()` 안에서 시작한다. 실제 공개·외부 전송, 배포 경로·철회·캐시 제거 방식은 **확인 필요**이며 별도 결정 전 실행하지 않는다. 이는 안 A의 실시간 공개 뷰와 다른 비용·최신성 선택이다.

### B5. 단계적 도입과 되돌리기

다음은 구현 PR을 나누기 위한 **5단계 제안**이며 SQL 파일 수·일정 추정은 아니다. 과거 포털의 표·학생 데이터·인증 세션은 가져오지 않고 합성 자료로 검증한다.

| 단계 | 추가 범위 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1 | 공통 사람·계정 연결·학사 차원과 확정 규칙 연결 | 두 학교의 읽기·쓰기 및 학교 간 FK 거부, 동명이인·개명·다중 계정 시험 |

**결정 전에 확인할 것:** 학교의 실제 마감·정정 승인 절차, P/F·제외·반올림 등 통계 규칙, 보호자 동의·철회, 학생 계정의 라이선스 처리, 익명 공개·철회 경로, 예상 동시 편집 수·성적 행 수·보존 기간. 모두 현재 **확인 필요**다. 빠른 핵심 모델 도입이 우선이면 A, 마감/정정과 다용도 발행이 초기 필수라면 B를 검토한다. A 채택 뒤 정정 추적·다용도 발행 요구가 커지면 B를 재검토하고, B 채택 뒤 승인·보관 비용이 효익보다 커지면 아직 미도입인 공개 산출물 단계를 재검토한다.

안 B를 선택할 때는 기존 「확인 방법」에 다음 시나리오를 추가한다. 이는 **구현 후 통과해야 할 조건**이며 이번 문서 PR에서 통과한 시험이 아니다.

- 두 학교의 표·뷰·명령 함수에 읽기/쓰기 양방향 거부, 같은 학교의 다른 학생·다른 수업 참조 거부.
- 두 교사의 동시 저장/마감, 마감 직전 수강·제외 변경, 중복 요청, 자식 행 실패를 주입해 부분 마감과 통계 불일치가 없는지 확인.
- 개명·표기 판 변경·성적 정정 뒤 이전 마감 판·발행본의 값과 해시가 불변인지 확인. 구판의 자식 추가와 수정·삭제도 거부.
- 담당 해제·계정 연결 철회·보호자 관계 만료가 다음 요청부터 반영되는지, 학생 역할 추가로 기존 문서·구성원 목록이 넓게 열리지 않는지 확인.
- 필수과목 생성 계기와 1,000행 초과 전체 모집단 계산, 학교급 범위, 내보내기 props·메타데이터 누출, 공개 철회 경로를 합성 자료로 검증.

- 새 마이그레이션 여러 개(타임스탬프 이름). 기존 14~17차 표는 유지하고, `terms`는 확정 규칙(`school_rules`)에서 만든다.
- 학생 실데이터는 이 결정 뒤에도 합성 자료로 시험하고, 실제 학교 자료를 넣는 것은 개인정보 처리 결정 뒤.

## 확인 방법

- 각 표의 RLS 양방향 테스트, 복합 FK 거부 테스트
