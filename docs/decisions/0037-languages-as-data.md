# 0037. 언어는 데이터로: 언어를 더할 때 코드·구조를 바꾸지 않는다

- 상태: 채택
- 날짜: 2026-11-27
- 제안: Claude(관제)
- 결정: 사용자(2026-11-27)
  - "이 시스템은 기본적으로 영어권에서도 쓸 수 있도록 모든 기능들은 영/한 공통으로 언어전환이 가능하도록 제작하자."
  - "언어는 한/영 만으로 처음부터 설계하면 나중에 설계 확장이 힘들 것 같네. 어떤 언어든 추가할 수 있으니 언어를 추가할 때마다 코드와 구조를 바꾸지 말고, 그냥 언어를 추가하면 바로 해당 언어로 작업이 가능하도록 하자."
  - "영어로 전환하는 작업은 미리 진행해 두도록 하고"
- 관련: ADR 0020(홈페이지 내용 자동 번역), 0025(학사 토대: 한국+미국 기준, 다른 나라는 출력 프로필), 0032(AI는 구독)

## 배경
- 데이터 쪽은 이미 여러 언어를 담는다.
  - 학사 정의 제목: `{ko, en}`
  - 학교 문서 언어
  - 홈페이지 번역 상태
- 화면 글자는 한국어로 코드에 박혀 있다(화면 파일 76개, 한글 줄 약 1,500).
- 홈페이지 지원 언어는 코드·DB 검사에 `ko·en·th` 세 개로 고정되어 있다.

## 결정
1. **언어 목록 표** `languages`
   - 칸: 코드(BCP 47) · 그 언어로 쓴 이름 · 글 방향(ltr/rtl) · 대체 언어 · 사용 여부
   - 전체 관리 → '언어·번역'에서 한 줄 더하면 바로 전환 목록에 나온다.
2. **번역 사전** `ui_messages`: (언어, 이름표) → 글자
   - 기준 문구(한국어)와 이름표 목록은 코드 `src/lib/i18n/catalog.ts`에 둔다. 새 화면이 새 문구를 만들 때만 바뀐다.
   - 다른 언어는 영어를 포함해 모두 사전에 둔다. 코드에 언어별 분기가 없다.
3. **대체 순서**: 고른 언어 → 그 언어의 대체 사슬 → 영어 → 한국어. 번역이 덜 된 언어도 바로 쓸 수 있다.
4. **채우기 형식**: `{이름}`, `{n, plural, one {…} other {…}}`. 복수형·날짜·숫자는 그 언어 규칙(`Intl`)을 따르고, 오른쪽→왼쪽 언어는 `dir`이 자동이다.
5. **언어 고르기**: 사용자 설정(`user_preferences.ui_lang`) → 쿠키 → 브라우저 언어 → 한국어. 위 막대·로그인 화면에 전환 단추가 있다.
6. **기본 묶음** `i18n/<언어>.json`
   - 배포·시드 때 사전의 빈 칸을 채우고, 묶음이 넣은 번역(`updated_by` 없음)은 묶음 글이 바뀌면 새 글로 바꾼다. 관리 화면이나 학교 AI가 고친 번역(`updated_by` 있음)은 덮지 않는다(104차, 사용자 결정 2026-11-27: 코드에서 고친 영어가 운영에 들어가지 않던 문제).
   - 그래서 새 환경(전용·독립 DB, ADR 0035)에도 같은 번역이 깔린다.
   - 묶음 파일이 있는 언어(지금 en·th)는 빠짐없이 채운다: 새 이름표는 `scripts/i18n-add.mjs`가 모든 묶음에 함께 넣고, 빠지면 시험이 CI를 막는다(2026-11-28 사용자 결정 "새 문구도 태국어 자동으로 채워지게"). 번역은 문구를 더하는 세션(구독 AI)이 함께 한다(ADR 0032). 관리 화면에서만 더한 언어는 대상이 아니다(대체 언어로 보임).
7. **번역 채우기**: 관리 화면에서 JSON으로 내보내고 넣는다. 구독 세션(관제·전담 세션·학교 AI)이 채우고, 유료 번역 API는 쓰지 않는다(ADR 0032).
8. **새 한국어 하드코딩 금지**: `npm run lint:i18n`(CI)
   - 화면 파일(TSX)의 한글 줄 수를 기준선보다 늘리면 실패한다.
   - 기존 줄은 화면 묶음별로 옮기며 기준선을 낮춘다.
   - 공개 홈페이지 렌더러(학교 내용)와 디자인 원형은 뺀다.
9. **언어는 세 갈래로 따로 정한다**
   - 화면 언어: 사람마다
   - 기록·발행 문서 언어: 학교·출력 프로필(ADR 0025)
   - 홈페이지 언어: 학교 설정
   - 홈페이지의 `ko·en·th` 고정 목록은 이 표를 보도록 바꾼다(홈페이지 세션과 맞춰 다음 단계).

## 고려한 안
| 안 | 판단 |
| --- | --- |
| next-intl 등 라이브러리 + 언어별 JSON 파일 | 기각: 언어를 더할 때 파일 추가와 배포가 필요하다(사용자 요구와 다름). 라우팅·미들웨어 변경도 크다 |
| 한·영 두 칸을 코드에 두기 | 기각: 사용자 요구가 "어떤 언어든" |
| **DB 사전 + 코드 이름표 목록(채택)** | 언어 추가는 데이터, 문구 추가는 코드. 시험으로 이름표·채우기 자리 일치를 지킨다 |

## 결과
- 좋은 점
  - 언어를 관리 화면에서 더하고 번역을 채우면 끝난다.
  - 영어권 학교·외국인 교사가 같은 화면을 자기 언어로 쓴다.
- 비용
  - 기존 화면 문구 약 1,500줄을 이름표로 옮기는 일이 남았다. 다국어 전환 전담 세션이 화면 묶음별로 옮기면서 영어 번역을 함께 채운다.
  - 서버 오류 문구(한국어)도 같은 방식으로 옮겨야 한다(다음 단계).
- 다시 검토할 조건: 사전이 커져 화면마다 전체 사전을 넘기는 것이 무거워지면 이름표 영역별로 나눠 넘긴다.
