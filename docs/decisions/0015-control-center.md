# 0015. 관제 센터: 결정 요청함과 지시 전달

- 상태: 채택
- 날짜: 2026-11-23
- 제안: 사용자 지시
  - "세션들이 승인될 것을 물어본 상태에서 멈추기 일쑤다. 승인이 필요한 것은 관제 센터에서 요청건으로 별도로 올려놓고, 해야 할 다른 작업들을 하는 것이 좋겠다. 관제 센터에 승인, 지시 등의 대화를 통한 개발을 할 수 있는 길을 열어 놓고, 해당 센터에서 대화를 하면 해당 내용이 세션에 전달되거나 작업이 실행되도록 하자."
  - "개발·연구소의 할 일이 승인 대기 건인가? 그렇게 보이지 않는다. 세부 내용을 붙이고, 추가 요청사항을 넣어서 지시할 수 있도록."
- 결정: 사용자(2026-11-23), 구현 방식은 관제 세션(Claude)
- 관계: ADR 0010(점검 토큰)에 관제 표 쓰기 하나를 더한다. ADR 0013(관제 서브 세션)의 운영 규약을 바꾼다.

## 배경
서브 세션은 사용자 승인이 필요하면 그 세션 대화에서 묻고 멈췄다. 사용자는 세션마다 찾아가 답해야 했고, 개발·연구소 '할 일'은 사용자가 적어 두는 목록이라 승인 대기 건이 보이지 않았다.

## 고려한 안
| 안 | 내용 | 장점 | 단점·위험 |
| --- | --- | --- | --- |
| **A. 웹 관제 센터 + 점검 토큰 쓰기 함수 (채택)** | DB에 요청·대화를 두고 `/admin/control`에서 답·지시. 세션은 점검 토큰으로 요청을 올리고, 관제가 지시를 세션에 전달(`send_message`·`create_session`) | 사용자가 한 화면에서 답함. 기록이 남음. 새 비밀 없이 이미 있는 점검 토큰 사용 | 웹에서 세션을 바로 깨울 수 없어 관제가 읽어 전달해야 함(전달 시점은 관제 대화·예약 확인) |
| B. 문서(DECISIONS.md)만 | 관제가 파일로 모으고 대화에서 물음 | 개발 없음 | 웹에서 볼 수 없음, 지시 전달 기록이 없음 |
| C. 별도 관제 토큰 | 점검 토큰과 다른 토큰·머리 | 권한 분리 명확 | 사용자가 환경에 비밀을 하나 더 넣어야 함 |
| D. 앱이 Claude API로 세션 호출 | 웹에서 바로 실행 | 즉시 | 유료, 세션 API를 앱에 연결하는 비밀 필요 |

## 결정
A. 점검 토큰으로 쓸 수 있는 것은 `control` 스키마 함수뿐이다(요청 올리기·보고·전달됨 표시·세션 등록). 이 함수는 관제 표(`control_*`)만 쓰고, 작성자를 `control`·`session`으로만 남긴다. 사람의 답·지시(`user`)는 로그인한 전체 관리자만 쓴다(RLS). 점검 계정의 화면 요청은 계속 읽기 전용이다.
D는 비용 승인 뒤 다시 본다. C는 점검 토큰이 여러 사람·환경에 퍼질 때 다시 본다.

## 영향
- DB: `control_sessions`·`control_requests`·`control_messages`(추가만, 전달됨 표시 한 번), 역할 `control_writer`, 스키마 `control`. 학교 자료가 아니므로 `school_id` 없음.
- 앱: `/admin/control`(관제 센터), `/api/admin/control/*`(사람), `/api/control/*`(점검 토큰). 개발·연구소 항목에 '세션에 지시'.
- 규약: 서브 세션은 승인을 기다리며 멈추지 않는다(AGENTS.md 변경 원칙, `docs/automation/SCHOOL-SESSIONS.md`). 전달 절차 `docs/automation/CONTROL-CENTER.md`.
- 되돌리기: 함수 실행 권한을 거두면(`revoke execute on all functions in schema control from agent_request`) 웹 화면만 남는다.
