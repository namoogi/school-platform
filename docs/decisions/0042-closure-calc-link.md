# 0042. 마감 연결: 수업 마감이 계산식 판 결과로 굳힌다(앱 계산 + DB 대조)

- 상태: 채택
- 날짜: 2026-11-27
- 제안: Claude(관제)
- 결정: 사용자(2026-11-27, 선택지 중 '앱 계산 + DB 대조 (추천)')
- 관련: ADR 0025(F2 수업 마감 판), 0040(계산식 판 '다음 단계: 마감 연결'), 0041(국가 견본·보충 이수 입력), Codex #166 P1
- 계기: 마감(`app.close_offering`)이 척도(`band_for`)만 보고 보충 이수·과목 출석률·P/F 판정을 보지 않았다. 그래서 40% 미도달 학생이 최소 성취수준 보장지도를 마쳐도 I·미이수로 굳었다(57차부터 있던 빈틈).

## 고려한 안
| 안 | 내용 | 판단 |
| --- | --- | --- |
| **A. 앱 계산 + DB 대조(채택)** | 앱이 계산식으로 학생마다 결과를 낸다. DB가 입력을 원장에서 다시 조립해 앱이 쓴 입력과 같은지 대조한다. 식·입력·결과를 마감 판에 얼린다 | 계산기가 하나(`expr.ts`)라 어긋날 일이 없다. 얼린 식 + 얼린 입력으로 누구든 다시 계산해 확인할 수 있다 |
| B. DB 안에 같은 계산기 | plpgsql로 계산기를 한 벌 더 만든다 | 일이 2~3배이고, 두 계산기가 같은 답을 내는지 계속 시험해야 한다 |
| C. 사람 판정 덮어쓰기만 | 마감 때 관리자가 학생별 성취도·이수를 고친다 | 빠르지만 계산식 판이 마감과 따로 논다 |

## 결정
1. **보충 이수 사건** `remediation_events`
   - 종류: 최소 성취수준 보장지도 `achievement`, 과목 출석 미달 추가학습 `attendance`. 값은 마쳤는지(참·거짓)와 메모.
   - 추가만 하고, 가장 최근 사건이 현재 값이다. 담당 교사·학교 관리자가 기록하고, 수강 중인 학생만 받는다(`app.record_remediation`).
2. **계산 입력 조립** `app.offering_calc_inputs(학교, 수업)`
   - 수강 중인 학생마다 계산식 입력(ADR 0040 모양)을 만든다.
     - 과목 총괄 축 평가 항목(코드 → 점수·만점·가중치)
     - 역량 축 수준 코드
     - 과목 출석률: 이 수업 교시 기록 중 결석·결과가 아닌 비율. 출석인정 사유는 출석으로 치고, 기록이 없으면 null
     - P/F(개설 또는 학생 선택), 보충 이수, 학점
   - 담당 교사·학교 관리자만 본다.
3. **마감** `app.close_offering`에 `calc = { code, version, results }`를 받는다.
   - DB는 입력을 다시 조립해, 학생마다 앱이 쓴 입력과 같은지 본다(jsonb 같음). 다르면 409다. 그 사이 점수·출결·보충 이수가 바뀐 것이다.
   - 거부하는 경우: 빠진 학생(409), 수강하지 않는 학생, 틀린 모양·등급 글자.
   - 결과 해석
     - 등급 = 식의 `level`
     - 이수: `passed` 참은 completed(학점 인정), 거짓은 failed, null(자료 없음)은 incomplete
     - 식에 `passed` 칸이 없으면(중학교처럼 과목 이수 판정이 없는 학교) 점수나 등급이 있을 때 completed, 없으면 incomplete다.
     - 원점수·최종 점수 = 식의 `score`. 몰래 반올림하지 않는다. 소수 셋째 자리 이하가 있으면 거부하고, 식에 `round`를 적게 한다. 얼린 식과 입력으로 다시 계산했을 때 값이 똑같아야 하기 때문이다.
   - 마감 판에 `calc_code`·`calc_version`·`calc_spec`, 결과 행에 `calc_input`을 얼린다.
   - 계산식 없이 마감하면 이전 동작(척도)이다.
4. **마감과 쓰기를 줄 세운다**(Codex #169).
   - 마감은 수업 단위 잠금을 혼자 잡는다. 마감 입력이 되는 쓰기(평가 결과·이 수업 교시 출결·보충 이수)는 같은 잠금을 함께 잡는다(쓰기 표의 앞 트리거).
   - 그래서 마감은 진행 중인 쓰기가 끝난 뒤 원장을 읽는다. 마감을 기다린 결과 쓰기는 '마감 뒤에는 관리자 + 사유' 규칙을 다시 확인받는다.
   - 과목 출석률은 잘라내지 않는다(float8). 앱의 2/3·1/3과 같은 값이 되어 경계 비교가 맞다.
5. **중간값 계산 순서는 서로 가리키는 관계로 정한다**(`letOrder`).
   - 이번에 발견했다: DB(jsonb)는 저장할 때 객체 칸 순서를 바꾼다(짧은 이름부터). 적힌 순서로 계산하던 104차 계산식은 저장 뒤 결과가 달라질 수 있었다.
   - 서로를 가리키는 중간값은 검사가 막는다.
   - 견본마다 DB 왕복 뒤 같은 결과인지 시험한다.
6. 화면: 성적 → 수업 마감에 '계산식' 고르기(학교 계산식 판이 있을 때), '보충 이수' 칸(담당 교사·관리자). 이름표 ko·en.

## 위협 모델 (Codex #169 지적에 대한 판단)
- DB는 결과(`score`·`level`·`passed`)를 다시 계산하지 않는다. 그래서 마감 함수를 직접 부를 수 있는 쪽은 입력은 그대로 두고 결과만 바꿔 넣을 수 있다.
- 사용자는 이 함수를 직접 부를 수 없다.
  - DB 연결은 서버만 갖는다(ADR 0002). 이 앱은 Supabase Data API(PostgREST)를 쓰지 않고, 사용자에게 DB용 JWT를 주지 않는다. JWT 클레임은 서버가 `asUser` 트랜잭션 안에서 넣는다.
  - 앱 경로(`POST /api/grades {action:'close'}`)는 계산식 이름만 받는다. 계산은 서버가 하고, 결과를 밖에서 받지 않는다.
- 남는 위험: DB 소유 권한이 있는 운영자다. 이 권한은 표에 직접 쓸 수도 있으므로 이 함수만의 문제가 아니다. 대응은 사후 재현 점검이다(아래 '다음').
- 다시 검토할 조건: Data API를 켜거나, 학교 쪽에 DB 접속을 열거나, 학교 AI가 마감 함수를 직접 부르는 길을 만들 때. 그때는 결과를 DB가 계산하거나(안 B) 서버 서명을 붙인다.

## 하지 않은 것 (다음)
- **재현 점검**: 계산식으로 마감한 판마다 얼린 식과 입력으로 다시 계산해 결과가 같은지 확인하는 점검 명령(운영 정기 점검·CI 연습 이전).
- 학생 판정 입력(`entry`)·이전 기록 계승(`prior`)을 마감 입력에 넣기. 드리미 방식의 학생별 P/F 판정 칸이 필요하다.
- 수업 갈래·학교급마다 기본 계산식을 묶어 마감 화면에서 미리 고르기.
- 모집단 값(석차등급·분포비율)을 마감 판 통계에 붙이기(`population.ts`).
- 학년도 범위 계산식(평균·출석 판정).
