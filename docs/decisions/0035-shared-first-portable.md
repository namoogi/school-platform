# 0035. 공용 DB를 기본으로, 학교 맞춤은 정의·규칙·계산식으로, 학교는 언제든 전용·독립으로 옮길 수 있게

- 상태: 채택
- 날짜: 2026-11-27
- 제안: Claude(관제)
- 결정: 사용자(2026-11-27)
  - "대안학교는 각 학교별로 교육과정이 조금씩 다 다르고 성적을 산출하는 방식도 다 다르다. 그래서 AI로 맞춤형 체제로 가려고 했던 것이고. 공용으로 하되 AI로 개별 수정이 되도록 지원은 되지 않을까?"
  - "기본정보는 최대한 확장형태로 만들어 놓으면 개별학교는 안 쓰더라도 DB 구조를 바꾸거나 확장할 필요는 없겠지. 그리고 공용 DB를 쓰다가 전용이나 독립으로 이전할 수도 있겠지? 그렇게 한다면 미리 설계를 해 놓아서 DB 이전이 쉽게 이루어지도록 하고."
- 관련: ADR 0019(규모), 0025(학사 토대·확장 사다리), 0027(기본판·학교 사본), `docs/research/backend-tenancy-2026-11.md`, `docs/research/system-tiers-2026-11.md`

## 배경
- 대안학교는 교육과정과 성적 산출 방식이 학교마다 다르다. 선생님은 학교 AI가 학교마다 맞춤으로 고치는 체제를 원한다.
- 드리미포털은 프로젝트 하나 안에서 앱마다 스키마 칸을 두고 AI가 표·코드를 자유롭게 만든다. 이것은 **한 학교 안**의 앱들이라 견딘다.
- 여러 학교가 한 DB를 쓰면서 각 학교 AI가 표·코드를 만들면 문제가 생긴다. 한 학교의 실수(느린 질의·권한 누락)가 다른 학교로 번진다. 포털도 "학교 경계는 DB로 가르라"고 권했다.

## 결정
1. **공용 DB가 기본이다.** 대부분의 학교는 공용형으로 쓴다(원가가 가장 낮고 업데이트가 한 번).
2. **학교 맞춤은 '설정값'으로 한다. 학교 AI가 DDL·코드를 올리지 않는다.**
   - 핵심 표: 모든 학교에 있는 공통 사실(사람·학적·수업·결과·출결·마감 판·발행본). 형이 정해진 표로 둔다.
   - 학교 사본: 기본판에서 복제한 코드 목록·척도·정책·규칙 판(ADR 0027). 학교가 고쳐도 기본판은 바뀌지 않는다.
   - 정의 엔진: 학교 고유 기록 유형·양식·화면·출력·흐름(ADR 0025 F5). 검사기를 통과한 것만 들어간다.
   - **계산식 판(다음 차시)**: 이수 기준·성적 산출 방식을 학교 AI가 선언형 식으로 쓴다. 관리자가 확정한 판만 마감에 쓰고, 마감 판에 계산식 판 번호를 남긴다.
   - 여러 학교에 새로 필요한 사실이 생기면 플랫폼이 모든 학교를 위해 한 번 표를 더하고 기본은 꺼 둔다(확장 사다리 E6). 학교별 DB 구조 변경은 없다.
3. **학교는 언제든 옮길 수 있어야 한다.** 공용 → 전용형(그 학교 전용 프로젝트) 또는 독립형(학교·기관 명의 계정·자체 서버).
   - 같은 코드·같은 마이그레이션을 쓴다. 옮기는 것은 '어디에 사는가'뿐이다.
   - 도구: `scripts/school-move.mjs`
     - export: 학교 한 곳의 모든 행 + 관련 계정·기본판을 한 묶음으로 꺼낸다.
     - import: 같은 판까지 올린 빈 자리에 넣는다. 트리거를 잠시 끄고 넣은 뒤 고아 연결을 검사한다.
     - verify: 표마다 행 수·내용 지문을 비교한다.
   - 절차: `docs/SCHOOL-MOVE.md`
4. **이전 가능성 문(門)**: `tests/school-move.test.ts`가 CI에서 매번 두 가지를 확인한다.
   - **연습 이전**: 예시학교 A를 빈 DB로 옮겨 내용 지문 동일, 고아 연결 없음, 다른 학교 행 없음, RLS·마감 판 보호 유지를 본다.
   - **구조 규칙**: 새 학교 표는 UUID 번호를 쓴다. 학교 표끼리의 연결에는 `school_id`를 함께 묶는다. 지금 있는 예외는 목록에 이유와 함께 두고 줄이기만 한다.
5. 확장형(학교 전용 별관 프로젝트에서 학교 AI가 표·코드를 만드는 것)은 **정의·계산식으로 안 되는 실제 요구가 생길 때** 드리미학교 1곳으로 시범한다. 그때 별도 ADR로 정한다.

## 고려한 안
| 안 | 내용 | 판단 |
| --- | --- | --- |
| 공용 + 학교마다 스키마(포털식) | 학교 AI가 공용 DB 안 자기 스키마에 표·코드 | 기각: 장애·느림이 모든 학교로 번지고, 한 학교만 복원할 수 없다 |
| 학교마다 프로젝트(전원 전용) | 격리 최강 | 보류: 원가 10배 이상, 업데이트·감시가 N번(1,000곳이면 월 $10,000+) |
| **공용 + 설정값 맞춤 + 이전 가능(채택)** | 위 결정 | 원가·관리 최소, 맞춤 요구 대부분 충족, 큰 학교·특수 요구는 옮겨서 해결 |

## 결과
- 좋은 점: 학교가 늘어도 DB 구조는 하나다. 학교 AI의 맞춤이 다른 학교에 번지지 않는다. 옮길 수 있음이 시험으로 계속 보장된다.
- 비용: 새 학교 표를 만들 때 UUID·복합 외래키 규칙을 지켜야 한다. 정의·계산식으로 담을 수 없는 요구는 플랫폼 개발(E6)이나 확장형을 기다린다.
- 남은 일
  - 계산식 판 구현(다음 차시). 선생님이 실제 성적 산출 규칙 예시를 주면 그 범위에 맞춘다.
  - 예외 목록 줄이기: 정정 사슬 5개를 복합 외래키로 바꾸고, 로그 표의 순번 번호는 셀 합치기 전에 정리한다.
  - 운영에서 실제 이전을 처음 할 때 확인할 것
    - Supabase에서 `session_replication_role` 설정 권한이 있는지 [확인 필요]
    - R2 파일 복사 시간
    - 로그인 공용 유지(전용형) / 학교 자체 로그인(독립형) 방식
- 다시 검토할 조건: 학교 AI가 정의·계산식으로 표현하지 못하는 요구가 반복되면 확장형 시범을 앞당긴다.
