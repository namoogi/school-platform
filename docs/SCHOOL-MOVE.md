# 학교 옮기기 (공용 → 전용·독립) — ADR 0035

학교 한 곳을 공용 DB에서 다른 DB(그 학교 전용 Supabase 프로젝트, 또는 학교·기관 명의의 DB)로 옮기는 절차다.
코드와 마이그레이션은 같고, 사는 곳만 바뀐다.

> **주의** 꺼낸 묶음 파일에는 그 학교의 학생·교직원 개인정보가 모두 들어 있다.
> - `.school-move/` 아래에 두고(커밋되지 않음) 옮긴 뒤 지운다.
> - 메일·채팅으로 보내지 않는다.
> - DB 주소·비밀번호는 환경 변수로만 넘기고 화면·기록에 남기지 않는다.

## 1. 준비
0. 전체 관리 → 등급(`/admin/placements`)에서 그 학교의 등급을 정하고 진행 상태를 '정함'으로 둔다(ADR 0038). 새 프로젝트를 만들면 비용이 생기므로 그 전에 사용자 확인을 받는다.
1. 대상 DB를 만든다.
   - 전용형: 같은 Supabase 조직에 프로젝트를 추가한다.
   - 독립형: 학교·기관 명의의 계정에 만든다.
2. 대상 DB에 같은 판까지 마이그레이션을 적용한다: `DATABASE_URL=<대상> node scripts/migrate.mjs`
3. 원본에서 그 학교를 잠시 '이용 중지'로 둔다. 옮기는 동안 새 기록이 생기지 않게 하기 위해서다.

## 2. 꺼내기 · 넣기 · 확인
**DB 주소와 비밀번호는 따로 넣는다**(78차 규약: 특수기호 오류 방지).
- `SOURCE_DATABASE_URL`·`TARGET_DATABASE_URL`: 주소는 비밀번호 자리를 `[YOUR-PASSWORD]` 그대로 둔다.
- `SOURCE_DATABASE_PASSWORD`·`TARGET_DATABASE_PASSWORD`: 비밀번호는 이 변수에 넣는다.

| | 만드는 곳 | 다시 볼 수 있나 | 보관 |
|---|---|---|---|
| 원본(공용) 비밀번호 | 이미 있음. GitHub Environment `production`의 `DATABASE_PASSWORD`와 같은 값 | Supabase는 다시 보여 주지 않음. 잊었으면 Supabase → Project Settings → Database → Reset database password(바꾸면 운영 비밀값도 함께 바꿔야 함) | 비밀번호 관리 앱에 따로 |
| 대상 비밀번호 | 새 프로젝트를 만들 때 Supabase가 정하게 하거나 직접 입력 | **만들 때 한 번만 보임**. 그 자리에서 복사 | 비밀번호 관리 앱에 따로. 채팅·메일·저장소에 두지 않음 |

```bash
mkdir -p .school-move
SOURCE_DATABASE_URL=<원본> node scripts/school-move.mjs export <학교 주소 이름> .school-move/<학교>.json
TARGET_DATABASE_URL=<대상> node scripts/school-move.mjs import .school-move/<학교>.json --status active
SOURCE_DATABASE_URL=<원본> TARGET_DATABASE_URL=<대상> node scripts/school-move.mjs verify .school-move/<학교>.json
```
- 넣기는 그 학교가 아직 없는 자리에만 한다.
  - 원본·대상의 마이그레이션 목록이 양쪽으로 똑같아야 넣는다. 대상에만 있는 마이그레이션도 거부한다.
  - 1-3에서 원본을 '이용 중지'로 두었으므로, 대상에서 열 상태를 `--status active`(또는 `trial`)로 정한다. 정하지 않으면 이용 중지 묶음은 넣지 않는다.
  - 대상에 다른 학교가 이미 있으면(셀) 세 가지를 먼저 본다: 같은 판 번호의 기본판 내용이 다른지, 같은 메일·다른 id 계정이 있는지, 순번 번호 칸이 겹치는지. 하나라도 있으면 넣지 않는다(계정 합치기·번호 다시 매기기는 셀 합치기 단계의 남은 일).
  - (상세) 순번 번호 표(로그 등)의 번호가 겹치는지 먼저 본다. 겹치면 넣지 않는다. 번호 다시 매기기는 셀 합치기 단계의 남은 일이다.
  - 로그인 연결(`--auth`)
    - 기본 `reset`: 외부 로그인 연결을 비운다. 첫 로그인 때 확인된 메일로 다시 잇는다(초대와 같은 길).
    - 독립형처럼 로그인 서버가 바뀌면 반드시 `reset`이다. 옛 연결이 남으면 '다른 로그인 계정과 연결됨'으로 거부된다.
    - 같은 로그인 서버를 계속 쓰는 전용형만 `--auth keep`을 쓸 수 있다.
  - 트리거·외래키 검사를 잠시 끄고 넣는다(pg_dump와 같은 방식).
  - 같은 트랜잭션에서 고아 연결을 검사하고, 하나라도 있으면 모두 되돌린다.
- 확인은 학교 표마다 행 수와 내용 지문(md5)을 비교한다.
- 꺼낼 때 정리하는 것(묶음의 `normalized`에 적고, 확인 때 같은 칸은 빼고 비교한다)
  - 학교 밖을 가리키는 연결은 비운다. 예: 학교 없는 관제 세션, 연구소 항목, 다른 학교 행.
  - 로그인 정보는 이 학교 구성원·열람 계정만 들고 간다.
  - 전체 관리자(관제)와 그 밖의 사람은 이름표만 남긴다. 비밀번호·외부 로그인·관리자 권한을 빼고 메일을 가린다. 옮긴 DB에서 관제 계정이 관리자로 되살아나지 않게 하기 위해서다.

## 3. 파일·접속 옮기기
- R2 파일
  - 같은 버킷을 계속 쓰면 할 일이 없다.
  - 버킷을 바꾸면 `node scripts/school-move.mjs keys .school-move/<학교>.json`이 내놓는 객체 키를 하나씩 그대로 복사한다.
    - 지금 키는 `s/<학교 id>/<sha256>`이다(43차 이후).
    - 예전 자료는 `sha256/<sha256>`일 수 있다. 같은 키를 다른 학교가 함께 쓸 수 있으므로 원본에서 지우지 않는다.
- 앱 연결
  - 전용형: 그 학교 요청이 대상 DB로 가도록 학교 → DB 연결을 바꾼다. 셀 연결 표는 ADR 0019 단계 D이고 아직 없다.
  - 독립형: 같은 앱을 학교 환경에 배포하고 `DATABASE_URL`만 대상으로 둔다.
- 로그인
  - 전용형은 onschools 로그인을 그대로 쓴다.
  - 독립형은 학교 자체 로그인을 쓴다. 계정 행은 묶음에 함께 들어 있다.

## 4. 마무리
- 등급 화면에서 '옮김' 판을 새 주소와 함께 남긴다. 공용 앱의 그 학교 화면에 새 주소 안내가 뜬다.
- 대상에서 화면을 확인한다: 학교 관리자로 로그인해 기록·발행본을 연다.
- 원본의 그 학교 행은 바로 지우지 않는다. 일정 기간 보관한 뒤 보존 규칙에 따라 파기한다(ADR 0028).
- 묶음 파일을 지운다.

## 계속 옮길 수 있게 지키는 것
- CI의 `tests/school-move.test.ts`가 매번 확인한다.
  - 예시학교를 빈 DB로 옮겨 본다(연습 이전).
  - 새 학교 표가 UUID 번호와 `school_id` 복합 연결을 쓰는지 본다.
- 표를 더하다 이 시험에 걸리면 규칙대로 고친다. 그럴 수 없는 관제·로그 표만 예외 목록에 이유와 함께 넣는다.

## 아직 확인하지 못한 것
- 운영 Supabase에서 `session_replication_role` 설정이 허용되는지. 막히면 표 순서대로 넣는 방식으로 바꾼다.
- 큰 학교(행 수십만)의 묶음 크기·시간. 지금 도구는 한 파일 JSON이다. 커지면 표마다 나눠 흘려 보낸다.
